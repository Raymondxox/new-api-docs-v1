控制台内容配置位于 `/system-settings/content`，仅 Root 可访问。页面包含「数据看板」「公告」「API 地址」「FAQ」「Uptime Kuma」「聊天预设」和「绘图」七个分区。

本页既包含面向未登录访问者或普通用户的公开内容，也包含数据聚合和 Midjourney 请求处理等运行行为。它不负责配置账户角色、渠道能力或模型路由；相关权限和上游能力仍需在用户、渠道、模型及侧边栏配置中分别管理。

## 保存与公开边界

各分区独立保存，不是整页原子提交：

- 数据看板、聊天预设和绘图只提交发生变化的配置项，并按键逐项保存。一次操作可能出现前面的字段已成功、后面的字段失败的部分成功状态。
- 公告、API 地址、FAQ 和 Uptime Kuma 的启用开关在切换时会立即发起独立保存请求；列表中的新增、编辑、删除只是当前页面草稿，还需要点击该分区的「保存设置」。切换开关不等于同时保存尚未提交的列表。

公告、API 地址和 FAQ 只有在各自开关开启时才会加入公开的站点状态。Uptime Kuma 的公开状态只包含启用标志，监控详情由公开接口 `/api/uptime/status` 单独获取。聊天预设会作为 `chats` 始终包含在公开状态中。

浏览器会缓存 `/api/status` 的结果，并把缓存写入本地存储；默认缓存有效时间为 5 分钟。保存后应刷新页面或重新获取站点状态，再使用未登录窗口和普通用户账户验证，避免把旧缓存误判为保存失败。

<Callout type="warn">
  公告、API 地址、FAQ 和聊天模板会进入公开状态；Uptime Kuma
  的来源地址不会随状态接口直接返回，但公开的 `/api/uptime/status`
  会触发服务端访问已保存来源。不要在公开内容中写入 API Key、客户端密钥或管理员说明，也不要配置不可信的监控来源。
</Callout>

## 数据看板

数据看板分区控制消费数据是否额外聚合到 `quota_data`，以及后台把进程内缓存写入数据库的周期。

| 字段 | 行为与边界 |
| --- | --- |
| 启用数据导出 | 开启后，新生成的消费日志和任务消费日志会把额度数据加入当前进程的聚合缓存，并由后台任务写入 `quota_data`。关闭后停止新增这类聚合记录，但不会删除已经入库的历史数据。 |
| 导出间隔 | 可填写 1–1440 分钟，表示后台把聚合缓存写入数据库的间隔，不是控制台图表刷新频率。多实例部署时每个实例都有自己的进程内缓存。 |
| 默认时间粒度 | 可选择小时、天或周。该值会保存并通过公开状态返回，但当前新版看板未读取这个服务端字段；看板从浏览器本地偏好读取，未设置时固定使用 `hour`。修改后应在目标浏览器中手动调整图表偏好。 |

底层聚合记录的时间会截断到整点，因此数据的基础精度是小时。选择天或周只用于更高层级的展示与汇总，不会把底层采集精度改成天或周。

数据聚合依赖消费日志创建链路：如果「运维配置 → 记录额度使用」已关闭，普通 Relay 和消费类型的异步任务日志会在写日志前返回，即使这里开启数据导出也不会新增对应聚合。反过来，只关闭数据导出不会阻止原始消费日志写入，也不会自动清理 `quota_data`。修改开关或间隔后，应至少等待一个完整写入周期，再检查新数据是否按预期产生。

关闭数据导出后不再新增聚合桶；已经在内存但尚未刷盘的数据不会立即写入，后台循环会跳过保存，进程正常退出时也只在开关仍开启的情况下尝试刷盘。因此，这部分数据可能在重新开启并经过下一次写入周期前滞留，或随进程退出而丢失。

## 结构化公告

公告分区维护用于控制台概览和通知中心的结构化公告列表。通知中心读取按发布日期倒序排列后的前 20 条公告。

| 字段 | 限制与用途 |
| --- | --- |
| 公告内容 | 必填，最多 500 个字符；支持 Markdown/RichContent 展示。 |
| 发布日期 | 必填，保存为 RFC 3339 时间；后端仅用它进行倒序排序。 |
| 类型 | 可选 `default`、`ongoing`、`success`、`warning` 或 `error`，用于区分展示样式。 |
| 补充信息 | 可选，最多 100 个字符。 |

每次最多保存 100 条公告。发布日期不是定时发布计划：填写未来时间不会建立调度任务，也不会让公告在到达该时间前保持隐藏；只要启用公告并保存列表，未来日期的项目仍会进入公开列表，并因倒序排序靠前显示。

公告内容会通过 Markdown/RichContent 组件渲染并经过 DOMPurify 净化。可以使用常见 Markdown，但不要依赖任意 HTML、脚本、事件属性或嵌入代码能够执行。

<Callout type="info">
  本分区与「站点与品牌配置 → 系统公告」是两套独立内容。这里管理多条结构化公告；系统公告是一段单独的全局通知，二者不会自动同步。
</Callout>

## API 地址

API 地址分区用于向用户展示可用的实例地址或线路说明。每次最多保存 50 条，每条包含：

| 字段 | 限制 |
| --- | --- |
| URL | 必填，只接受 HTTP(S) 地址，最多 500 个字符。 |
| 线路说明 | 必填，最多 100 个字符。 |
| 描述 | 必填，最多 200 个字符。 |
| 颜色 | 从界面提供的颜色中选择，用于概览卡片样式。 |

启用后，概览页会提供复制、打开和测速等交互。浏览器端的延迟测试会以 `HEAD` 和 `no-cors` 方式请求目标，也可以跳转到外部 `tcptest` 服务进一步测试；结果会受到浏览器网络、CORS、代理和目标站点行为影响，不能替代服务端健康检查。

列表中的第一条 URL 还会作为概览页「首次 API 请求」示例的端点。排序前应把最适合普通用户复制使用的公网地址放在首位。

<Callout type="info">
  API 地址列表只负责展示和示例，不参与渠道选择、模型映射、负载均衡或 Relay 路由。要改变请求实际发往哪个上游，请在渠道和模型配置中处理。
</Callout>

## FAQ

FAQ 分区维护控制台概览页的折叠式常见问题。每次最多保存 100 条；问题必填且最多 200 个字符，答案必填且最多 1000 个字符。

问题和答案都会通过 Markdown 组件渲染并经过 DOMPurify 净化。可以使用链接、列表和代码等常见 Markdown 结构，但不应把 FAQ 当作可以执行任意 HTML 或 JavaScript 的内容区域。

建议每个条目只解决一个明确问题，并把账户、计费、模型和故障排查等内容分别组织。修改顺序后应在概览页确认折叠项的展示顺序和长文本在移动端的可读性。

## Uptime Kuma

Uptime Kuma 分区把一个或多个 Uptime Kuma 状态页聚合到控制台概览。每次最多保存 20 个分组。

| 字段 | 限制与用途 |
| --- | --- |
| 分类名称 | 必填且不可重复，最多 50 个字符。 |
| Uptime Kuma 地址 | 必填，只接受 HTTP(S) 地址，最多 500 个字符；填写可由 New API 服务端访问的根地址。 |
| Slug | 必填，最多 100 个字符，只能包含字母、数字、下划线和连字符。 |

后端兼容保存可选的 `description` 字段并限制为 200 个字符，但当前管理表单没有提供该字段，概览也不展示它；通过现有表单新增或编辑分组时，只能维护上表三项。

客户端请求 `/api/uptime/status` 时，New API 服务端会为每个分组访问：

```text
{Uptime Kuma 地址}/api/status-page/{slug}
{Uptime Kuma 地址}/api/status-page/heartbeat/{slug}
```

单个 HTTP 请求的超时为 10 秒，整次聚合处理的上下文超时为 30 秒。某一分组访问失败时，该分组通常返回空的监控列表，接口整体仍可能返回成功；因此“接口成功”不表示每个状态来源都可用。

启用开关主要控制概览面板是否展示并请求监控数据。`/api/uptime/status` 本身是公开接口，当前处理器不会再次检查启用标志；关闭开关后，如果仍有人直接调用该接口，服务端仍可能访问已保存的来源。若需要停止保留和访问这些来源，应同时清空分组并保存。

<Callout type="warn">
  只配置可信的 Uptime Kuma 地址。New API 服务端会主动访问这些 URL，而该链路使用普通 HTTP 客户端，不受「安全与限制配置」中的 SSRF 受保护客户端统一拦截。不要把可由低信任方控制、会解析到敏感内网或云元数据地址的 URL 保存到这里。
</Callout>

## 聊天预设

聊天预设用于生成用户可以直接打开的聊天客户端链接。可以使用可视化编辑器，也可以切换到 JSON 编辑器；底层格式必须是数组，且每一项必须恰好包含一个“客户端名称 → URL 或协议模板”键值对：

```json
[
  {
    "网页客户端": "https://chat.example.com/?base={address}&key={key}"
  },
  {
    "Cherry Studio": "cherrystudio://providers/api-keys?v=1&data={cherryConfig}"
  }
]
```

可视化编辑器要求客户端名称和模板均非空。模板可以是 HTTP(S) 网页、自定义协议，或 `fluent...` 类型的 FluentRead 集成。

### 使用位置与打开方式

- 用户侧边栏中的聊天入口会读取这些预设，但仍受全局侧边栏模块和用户个人侧边栏设置影响。需要密钥的预设会从 Token 列表第一页（最多 50 条）中查找第一个已启用 Token，再读取它的真实密钥。
- API Token 列表的行操作菜单会读取所操作行的真实 Token，并使用该 Token 生成聊天入口；它不受侧边栏自动选择结果影响，即使该行已禁用也仍可读取并注入其密钥。
- 从侧边栏打开 HTTP(S) 预设时，页面会在站内 iframe 中加载；自定义协议会交给浏览器或操作系统中的外部应用处理。从 Token 行菜单打开时，普通网页和自定义协议都会通过新窗口交给浏览器处理。
- FluentRead 预设不会显示在普通侧边栏中；从 Token 行操作触发时，前端通过 `fluent:prefill` 事件把配置交给相应集成。当前实现的密钥前缀处理可能重复添加 `sk-`，应在目标扩展中核对实际载荷，不要仅根据成功提示判断配置正确。

### 模板占位符

| 占位符 | 替换内容 |
| --- | --- |
| `{address}` | 当前实例服务器地址，并进行 URI 编码。 |
| `{key}` | 当前入口确定的完整 API Token；Token 行操作使用该行 Token，侧边栏入口使用前述第一个已启用 Token。前端会在需要时补上 `sk-` 前缀。 |
| `{cherryConfig}` | 包含 `id`、`baseUrl` 和 `apiKey` 的 Cherry Studio 配置 JSON，经 Base64 后再进行 URI 编码。 |
| `{aionuiConfig}` | 包含 `platform`、`baseUrl` 和 `apiKey` 的 AionUi 配置 JSON，经 Base64 后再进行 URI 编码。 |
| `{deepchatConfig}` | 包含 `id`、`baseUrl` 和 `apiKey` 的 DeepChat 配置 JSON，经 Base64 后再进行 URI 编码。 |

`Chats` 通过公开状态返回的是模板本身，不包含某个用户的 Token。只有用户在侧边栏或 Token 菜单中主动打开预设时，前端才会读取相应 Token 并替换占位符。

三种 `*Config` 占位符按各自专用分支生成完整配置并立即返回结果；不要在同一模板中再依赖 `{address}` 或 `{key}` 继续替换。

<Callout type="warn">
  带密钥占位符的模板会把完整 Token 交给目标网页、协议处理程序、应用或扩展。目标可能把 URL 写入浏览器历史、服务日志、崩溃报告或分析系统。Base64 只是编码，不是加密。只配置可信目标，并优先使用权限、额度和有效期受限的测试 Token 完成验证。
</Callout>

## 绘图

绘图分区包含六个独立开关，发布绘图兼容标志，并控制部分 Midjourney 请求和任务结果的处理方式。

| 开关 | 实际行为与边界 |
| --- | --- |
| 启用绘图 | 向公开状态发布 `enable_drawing` 兼容标志，供能够识别该字段的客户端决定是否展示绘图能力。当前新版前端未发现对该字段的直接消费；`/mj` Relay 路由仍由服务端固定注册，不能把此开关视为关闭全部 Midjourney API 权限的后端鉴权总开关。 |
| 允许通知 Hook | 开启时允许把请求中的 `notifyHook` 交给上游；关闭时会在转发前删除该字段。回调地址可能向上游暴露本站地址或 IP。 |
| 允许账号过滤 | 开启时允许向上游传递 `accountFilter`；关闭时会在转发前删除该字段。 |
| 转发任务图片 URL | 开启后，把返回给客户端的任务图片 URL 改写为本站 `/mj/image/{id}`。它控制图片结果代理，不是渠道路由或通知回调地址配置。 |
| 清理模式参数 | 从 prompt 中移除字面量 `--fast`、`--relax` 和 `--turbo`，避免把这些模式参数继续交给上游。 |
| 后续操作检查成功状态 | 执行放大、变体等后续动作前，要求原任务状态为 `SUCCESS`；Modal 路径属于当前检查逻辑的例外。 |

六项设置按键逐项保存，可能出现部分成功。尤其是通知 Hook、图片转发和后续操作检查会改变请求或任务结果，修改前应记录原值，并使用测试渠道和测试任务验证完整链路。

<Callout type="warn">
  「启用绘图」是公开状态中的兼容标志，不替代渠道、Token、模型、分组及后端路由的权限控制。若要限制绘图 API，必须同时检查实际渠道能力和请求鉴权边界。
</Callout>

## 变更后验证

建议按以下顺序检查：

1. 保存一个分区后刷新当前页面，确认表单值与预期一致；如果一次保存修改了多个键，逐项确认是否存在部分成功。
2. 重新获取 `/api/status`，并使用未登录窗口和普通用户账户检查公开内容，排除 5 分钟状态缓存和本地存储的影响。
3. 同时开启数据导出和「运维配置 → 记录额度使用」，再产生可控的消费日志与任务消费日志；等待至少一个导出间隔后核对聚合数据，并分别关闭两个开关验证各自边界。
4. 分别检查公告排序、未来日期、通知中心前 20 条限制，以及 API 地址首项在请求示例中的使用。
5. 在概览页验证 FAQ 的 Markdown、长文本和净化结果，不要用脚本是否执行作为成功标准。
6. 从 New API 服务端网络验证每个 Uptime Kuma 地址和 Slug，并检查某一来源超时或失败时其他分组是否仍可显示。
7. 使用最小权限测试 Token 验证网页、自定义协议和所需客户端配置占位符，确认目标不会意外记录密钥。
8. 使用测试 Midjourney 渠道验证通知字段、账号过滤、图片代理、模式参数和后续动作状态检查，再逐步应用到生产流量。

## 截图建议

截图由站点维护者手动完成时，可优先记录以下界面，并遮盖 Token、内网地址、监控来源和其他敏感内容：

- 七个分区的顶部导航和数据看板配置；
- 结构化公告编辑器及公告类型选择；
- API 地址和 FAQ 列表编辑状态；

- 聊天预设可视化编辑器和 JSON 模式；

## 常见问题

- **切换启用开关后，刚编辑的列表内容没有生效**：开关会立即独立保存，但列表增删改仍需点击「保存设置」。返回分区确认列表是否已经提交。
- **保存成功后仍看到旧公告、API 地址或 FAQ**：刷新或重新获取 `/api/status`，并检查浏览器本地状态缓存；再确认对应启用开关已开启。
- **未来日期的公告提前出现**：发布日期当前只参与倒序排序，不是定时发布条件。需要暂不公开时不要保存到已启用列表中。
- **修改 API 地址后请求仍走原渠道**：该列表只用于展示、复制、测速和请求示例，不参与 Relay 选路。应到渠道和模型配置中调整上游路由。
- **Uptime Kuma 接口成功但某一组没有监控项**：检查 New API 服务端到目标地址的网络、状态页 Slug、证书和两个 Uptime Kuma API 路径；单组失败通常不会让整体接口失败。
- **关闭 Uptime Kuma 后服务端仍访问来源**：公开状态开关主要控制概览面板。若 `/api/uptime/status` 被直接调用，已保存来源仍可能被访问；清空分组并保存才能移除来源。
- **聊天入口没有显示**：检查聊天预设格式、全局侧边栏聊天模块、用户个人侧边栏设置和当前入口类型；FluentRead 项不会出现在普通侧边栏。
- **外部客户端没有收到正确配置**：确认使用了该客户端对应的占位符，并检查 URL 解码和 Base64 解码流程。Base64 内容仍包含完整 API Key。
- **关闭绘图后 `/mj` 路径仍可访问**：绘图开关不是路由级鉴权总开关。继续检查 Token、分组、模型、渠道和具体接口权限。
- **开启图片 URL 转发后通知回调没有变化**：该选项改写的是任务图片结果 URL，不是 `notifyHook`。通知字段由「允许通知 Hook」单独控制。
- **修改默认时间粒度后已有浏览器仍保持原选择**：当前新版看板不读取服务端的默认时间粒度字段，而是使用浏览器保存的图表偏好；清除或修改该浏览器的看板偏好后再验证默认值。
