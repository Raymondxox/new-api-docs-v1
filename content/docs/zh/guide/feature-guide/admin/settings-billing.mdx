计费与支付配置决定额度如何计量和展示、请求如何定价，以及用户可以通过哪些方式充值。Root 用户可从 **系统设置 → 计费与支付配置** 进入本页，对应地址为 `/system-settings/billing`。

<Callout type="warn">
  本页设置会直接影响请求扣费、用户余额和支付入账。生产环境修改前，请记录原配置并先在测试账号或支付网关的测试环境中验证；不要在截图、工单或公开文档中暴露 API Secret、Webhook Secret、RSA 私钥等敏感信息。
</Callout>

## 页面组成与保存方式

页面分为六个区域：

1. **额度设置**：新用户额度、预扣额度、邀请奖励和外部充值入口。
2. **货币与显示**：额度换算基准、货币模式和 Token 统计显示。
3. **模型定价**：模型、缓存、媒体、工具和动态表达式计费。
4. **分组定价**：分组倍率、充值倍率和 Auto 分组规则。
5. **支付网关**：支付合规、网关凭证、回调和充值规则。
6. **签到奖励**：每日签到开关和随机奖励范围。

大多数设置在点击保存后按字段逐项提交，因此一次保存并不是不可分割的整体事务。如果中途出现错误，请刷新页面并逐项确认实际生效的值。Waffo Pancake 的商店与产品绑定信息通过专用操作一起保存。

密钥输入框留空通常表示**保留已经保存的密钥**，不会清除原值。界面不会回显完整密钥；需要轮换密钥时，填写新值并重新保存。

> **截图建议：** 页面顶部与六个配置区域的整体布局。截图前请折叠或遮盖所有密钥字段。

## 修改前准备

在配置前确认以下信息：

| 项目 | 需要确认的内容 |
| --- | --- |
| 计费基准 | 模型按次价格、倍率价格或动态表达式，以及各用户分组的倍率 |
| 显示货币 | 使用美元、人民币、自定义货币还是原始 Token 数量 |
| 站点地址 | 公网可访问的 `ServerAddress`，支付服务商能否访问对应 Webhook |
| 支付资质 | 已阅读并确认支付合规声明，部署和收费行为符合所在地法律及上游服务条款 |
| 网关资料 | 商户号、API 密钥、Webhook Secret、产品 ID、公私钥和测试环境账号 |
| 验证账号 | 一个测试用户、一个测试模型，以及可用于小额支付或沙盒支付的方式 |

配置时应始终区分以下四个概念：

- **内部额度（quota）**：数据库和扣费流程使用的内部计量单位。
- **界面显示金额**：钱包、日志和价格页面把内部额度格式化后的结果。
- **模型账单价格**：按次、按 Token、按媒体或按工具调用计算出的使用成本。
- **网关实收金额**：用户在 EPay、Stripe、Creem、Waffo 等网关实际支付的金额。

修改显示货币不会自动重写已有用户额度，也不会代替支付网关的单价配置。

## 额度设置

### 字段说明

| 设置项 | 配置键 | 作用 |
| --- | --- | --- |
| 新用户初始额度 | `QuotaForNewUser` | 新用户创建后获得的初始内部额度 |
| 请求预扣额度 | `PreConsumedQuota` | Token 倍率计费时估算预扣量所使用的下限之一 |
| 邀请人奖励 | `QuotaForInviter` | 被邀请人完成注册后计入邀请人邀请额度的奖励 |
| 被邀请人奖励 | `QuotaForInvitee` | 被邀请人注册后直接计入其普通余额的奖励 |
| 外部充值链接 | `TopUpLink` | 为用户提供由管理员维护的外部充值入口 |
| 文档地址 | `general_setting.docs_link` | 站点文档链接，也可显示在控制台顶部导航中 |
| 免费模型预扣 | `quota_setting.enable_free_model_pre_consume` | 控制有效价格或有效分组倍率为零的请求是否执行预扣 |

这些输入使用内部 quota 单位，界面会同时显示格式化后的额度，方便管理员核对。

### 理解预扣与结算

`PreConsumedQuota` 不是“每次请求固定扣除的费用”。在普通 Token 倍率计费路径中，系统会根据输入 Token、请求中的最大输出量和该下限估算请求开始前需要冻结或扣除的额度；响应完成后，再按实际用量结算差额，多扣部分会退回。

按次固定价格和动态计费表达式有各自的预估逻辑，因此不能仅根据 `PreConsumedQuota` 推算所有请求的预扣结果。

关闭“免费模型预扣”后，只有有效模型价格或倍率为零、或者有效分组倍率为零的请求会跳过相应预扣。该开关不代表系统中的所有“免费请求”都不会产生任何费用。

### 理解邀请奖励

- 被邀请人的奖励会加入其普通额度。
- 邀请人的奖励会先进入 `aff_quota` 邀请额度，不会立即出现在普通余额中。
- 邀请额度至少达到一个 `QuotaPerUnit` 后，用户才能把它转入普通额度。
- 邀请奖励发放和邀请额度转移受支付合规确认保护。

如果尚未确认支付合规声明，正数的邀请人或被邀请人奖励不能通过通用设置接口保存。

## 货币与额度显示

### 字段说明

| 设置项 | 配置键 | 作用 |
| --- | --- | --- |
| 额度换算基准 | `QuotaPerUnit` | 每 1 个系统 USD 单位对应的内部 quota 数，默认 `500000`；当前页面只读 |
| 美元兑人民币汇率 | `USDExchangeRate` | CNY 显示模式下，把系统 USD 金额换算成人民币 |
| 显示模式 | `general_setting.quota_display_type` | 选择 `USD`、`CNY`、`CUSTOM` 或 `TOKENS` |
| 自定义货币符号 | `general_setting.custom_currency_symbol` | CUSTOM 模式使用的前缀或符号 |
| 自定义货币汇率 | `general_setting.custom_currency_exchange_rate` | `1 USD = X` 个自定义货币单位 |
| 按货币显示 | `DisplayInCurrencyEnabled` | 兼容旧版显示逻辑的开关 |
| 显示 Token 统计 | `DisplayTokenStatEnabled` | 控制界面是否展示 Token 用量统计 |

### 四种显示模式

| 模式 | 显示规则 |
| --- | --- |
| `USD` | 以美元显示，换算倍率按 `1` 处理 |
| `CNY` | 依据 `USDExchangeRate` 将系统 USD 金额换算为人民币 |
| `CUSTOM` | 使用自定义符号和 `custom_currency_exchange_rate` |
| `TOKENS` | 直接显示内部 Token／quota 数量 |

`TOKENS` 模式下原始 Token 显示优先。`DisplayInCurrencyEnabled` 和显示模式只改变界面的格式化方式，不会改变内部计费单位。

<Callout type="info">
  `USDExchangeRate` 用于界面显示换算；支付网关中的 `Price`、`UnitPrice` 等字段用于计算实际收款。两者用途不同，不应填写成同一字段后便假定网关金额会自动同步。
</Callout>

## 模型与工具定价

系统支持常规倍率、按次固定价格和动态计费表达式。实际采用哪条计费路径取决于模型的计费模式及其配置：常规路径中，配置了按次价格的模型优先按次计费，否则使用 Token／媒体倍率；启用动态表达式的模型按表达式计算。

### 常规定价字段

| 配置键 | 作用 |
| --- | --- |
| `ModelPrice` | 模型按次固定价格，单位为 USD／次 |
| `ModelRatio` | 输入 Token 等基础用量的倍率，不是直接填写的美元价格 |
| `CompletionRatio` | 输出 Token 相对于基础倍率的系数 |
| `CacheRatio` | 缓存读取 Token 的倍率 |
| `CreateCacheRatio` | 缓存创建 Token 的倍率；Claude 5 分钟和 1 小时缓存价格还会按实现规则派生 |
| `ImageRatio` | 图片相关用量倍率 |
| `AudioRatio` | 音频输入相关用量倍率 |
| `AudioCompletionRatio` | 音频输出相关用量倍率 |

项目的旧倍率基准中，`ModelRatio = 1` 约对应 `$0.002 / 1K tokens`。因此不能把倍率值直接理解为“每百万 Token 的美元价格”。配置后应使用测试请求和日志中的实际扣费进行核对。

价格按模型名匹配。系统会对部分模型名执行规范化，并支持实现中定义的前缀或通配匹配；配置时优先使用界面列出的真实模型名，不要假设任意正则表达式都能生效。

### 工具调用价格

`tool_price_setting.prices` 是 JSON 对象，单位为 **美元／1000 次调用**：

```json
{
  "web_search": 10,
  "web_search:gpt-4o*": 6
}
```

- `tool_name` 设置工具的默认价格。
- `tool_name:model_prefix*` 为特定模型前缀覆盖价格。
- 多个前缀都匹配时，更长的模型前缀优先。
- 值为 `0` 可终止该规则的价格匹配并关闭对应收费。
- 未配置的工具仍可能使用程序内置的默认价格。

### 动态与阶梯计费

动态计费由以下两个映射共同配置：

- `billing_setting.billing_mode`：把模型名映射到计费模式，例如 `tiered_expr`。
- `billing_setting.billing_expr`：把模型名映射到计费表达式。

表达式中的价格系数单位为 **美元／1M tokens**，与旧 `ModelRatio` 基准不同。常用变量包括：

| 变量 | 含义 |
| --- | --- |
| `p` | 未被单独类别变量计价的输入 Token |
| `c` | 未被单独类别变量计价的输出 Token |
| `cr` | 缓存读取 Token |
| `cc` | 缓存创建 Token |
| `cc1h` | 1 小时缓存创建 Token |
| `img` / `img_o` | 图片输入／输出用量 |
| `ai` / `ao` | 音频输入／输出用量 |
| `len` | 完整上下文长度，适合用作阶梯条件 |

表达式还可使用 `tier`、`param`、`header`、`has`、时间函数和数学函数。系统会根据表达式是否使用缓存、图片或音频等子类别变量，自动从 `p`、`c` 中排除对应 Token，避免重复计费；`len` 始终表示完整上下文长度，不受该排除逻辑影响。

表达式会同时用于请求预扣和最终结算。修改表达式相当于修改该模型的计费契约，必须先用已知输入、输出和缓存用量进行验证。

### 公开倍率和上游同步

开启 `ExposeRatioEnabled` 后，系统会通过 `/api/ratio` 公开倍率数据；关闭后，该接口会返回未启用。公开前应确认价格信息是否适合对外展示。

上游价格同步是一次手动操作：

1. 选择渠道和上游端点。
2. 获取上游价格。
3. 查看本地与上游的差异和冲突。
4. 勾选要采用的值。
5. 点击 **Apply Sync** 应用同步。

它不是后台持续同步服务；上游价格后续变更时，需要管理员再次执行同步。

## 分组定价与 Auto 路由

当前版本没有独立的“分组”管理页。分组由用户、API 密钥、渠道，以及本页的「分组定价」共同维护。配置时应区分以下层次：

- **用户分组**：用户账户所属的分组，是计算其可用目标分组和覆盖倍率的起点。
- **目标分组**：API 密钥最终选择的固定分组，或 `auto` 依次尝试的候选分组。
- **渠道分组**：渠道允许服务的分组；只有与当前目标分组匹配的渠道才会进入候选范围。
- **分组倍率**：在模型价格之上参与请求计费的倍率，也可以按用户分组覆盖目标分组倍率。

分组会影响用户或密钥可选的目标分组、渠道候选和计费倍率，但不会单独决定模型是否可见。模型公开或启用状态、渠道支持的模型、API 密钥模型限制和计费配置仍会共同生效。

| 配置键 | 作用 |
| --- | --- |
| `GroupRatio` | 用户实际使用目标分组时的基础计费倍率 |
| `TopupGroupRatio` | 用户充值时按其用户分组应用的倍率；未配置的分组通常回退为 `1` |
| `UserUsableGroups` | `分组 -> 描述` 的 JSON 映射，决定用户可以选择哪些分组 |
| `GroupGroupRatio` | 按用户分组覆盖其使用目标分组倍率的嵌套 JSON |
| `group_ratio_setting.group_special_usable_group` | 按用户分组追加、移除或覆盖可用目标分组 |
| `AutoGroups` | Auto 分组搜索顺序的 JSON 数组 |
| `MaxTokenAutoGroups` | 每个令牌保存的自定义 Auto 快照最多包含多少个分组 |
| `DefaultUseAutoGroup` | 新建令牌是否默认使用 Auto 分组 |

### 可用分组与覆盖规则

`UserUsableGroups` 的示例：

```json
{
  "default": "默认分组",
  "vip": "高优先级分组"
}
```

`GroupGroupRatio` 可为不同用户分组设置不同的目标分组倍率。例如，同一个 `vip` 目标分组可以对普通用户和合作伙伴使用不同倍率。它是按用户分组覆盖目标分组倍率的规则，不会改变用户账户本身所属的分组。

特殊可用分组设置支持三类键：

- `-:group`：从该用户分组的可用列表中移除 `group`。
- `+:group`：向可用列表添加 `group`。
- 普通分组键：直接添加或覆盖该分组的描述。

### Auto 分组

`AutoGroups` 定义系统搜索目标分组的顺序，`auto` 本身不是一个实际目标分组。请求使用 `auto` 时，系统会依据当前用户可用分组及 `GroupRatio` 中是否存在相应配置进行过滤、去重并保留原顺序。

API 密钥选择 `auto` 后，有两种顺序来源：

- **继承全局列表**：密钥没有保存自定义快照时，使用当前 `AutoGroups`。全局列表不受 `MaxTokenAutoGroups` 限制。
- **密钥级快照**：保存非空自定义顺序后，密钥使用这份快照。保存时会校验分组可用性、重复项和 `MaxTokenAutoGroups`；运行请求时仍会依据当前权限、可用分组和 `GroupRatio` 重新过滤，并按当前 `MaxTokenAutoGroups` 截断。

清空密钥的自定义列表会删除快照并恢复继承全局配置。如果已有自定义快照因后续权限或倍率配置变化而被过滤为空，系统不会自动回退到全局列表；应修改密钥快照或恢复继承。把密钥改为固定分组时，自定义 Auto 快照和跨分组重试设置也会被清除。

开启 `DefaultUseAutoGroup` 只会让之后新建的 API 密钥默认选择 `auto`，不会自动改写已有密钥。

### Auto 选择与跨分组重试

系统按 Auto 顺序为每个目标分组查找当前模型的可用渠道：

1. 如果某个分组根本没有该模型的可用渠道，选择阶段会直接继续检查后续分组，这与跨分组重试开关无关。
2. 找到渠道并发起请求后，普通重试仍先在当前分组内进行。
3. 只有 API 密钥使用 `auto`、已开启跨分组重试，并且当前请求仍满足重试条件时，达到全局 `RetryTimes` 阈值后的下一次尝试才从后续分组继续。

因此，跨分组重试不是“每次失败立即切换分组”，也不适用于固定分组的 API 密钥。实际重试还受错误类型、响应是否已经开始发送等通用重试条件约束。

### 推荐配置流程

1. 在本页配置 `GroupRatio`、用户可用目标分组、覆盖倍率和全局 Auto 顺序。
2. 在[渠道管理](./channel)中设置渠道所属分组及支持的模型。
3. 在[用户管理](./user)中分配用户分组，在用户的 API 密钥中选择固定分组或 `auto`。
4. 使用测试账号和 API 密钥发起请求；在日志记录已经生成且当前账户有查看权限时，通过[日志与异步任务](/zh/docs/guide/feature-guide/user/log)核对实际使用分组、渠道和扣费。

<Callout type="info">
  用户看不到模型或请求找不到渠道时，应同时检查模型状态、渠道模型列表、渠道分组、用户可用目标分组、API 密钥模型限制和价格配置，不要只检查分组倍率。
</Callout>

## 支付合规确认

在线支付、兑换码、订阅和邀请奖励等功能受支付合规确认保护。Root 用户需要在支付网关区域阅读声明并通过后台会话确认当前条款版本；API Access Token 不能代替后台会话完成确认。

确认记录会保存确认时间、用户 ID、客户端 IP 和条款版本。尚未确认时，支付表单会被禁用，并会限制以下能力：

- 在线充值网关；
- 兑换码创建、使用等相关功能；
- 订阅计划读取、支付和管理；
- 邀请奖励配置及邀请额度转移。

确认声明时，管理员需要确保：

- 已合法取得模型 API、账号、密钥和额度的授权；
- 只在上游授权范围内使用，不进行未经授权的转售或分发；
- 面向中国大陆公众提供生成式 AI 服务时，履行适用的备案、安全评估、内容安全、投诉处理、生成内容标识、日志留存和个人信息保护义务；
- 不利用系统实施违法、违反监管或平台规则、损害公共利益或第三方权益的行为；
- 独立承担部署、运营和收费行为产生的法律责任。

<Callout type="warn">
  页面中的合规提示不构成法律意见、合规审核结论或合法性保证。若部署场景、服务对象或收费方式存在疑问，请咨询具备相应资质的专业人士。
</Callout>

## 支付网关

各支付网关使用不同的凭证、启用条件和回调路径，不能只配置一个“通用回调”后便认为全部网关已经可用。生产环境建议使用 HTTPS，并确保反向代理不会拦截 Webhook 请求体或签名请求头。

### EPay

EPay 在满足以下条件时可用：

- 已确认支付合规声明；
- `PayAddress`、`EpayId` 和 `EpayKey` 均已配置；
- `PayMethods` 至少包含一种支付方式。

| 设置项 | 说明 |
| --- | --- |
| `PayAddress` | EPay 服务基础地址，必须以 `http://` 或 `https://` 开头 |
| `EpayId` / `EpayKey` | 商户 ID 和商户密钥 |
| `CustomCallbackAddress` | 可选的回调站点 origin，例如 `https://api.example.com`，不要包含接口路径；留空使用 `ServerAddress` |
| `Price` | 用户购买 1 个系统 USD 余额时收取的本地货币金额 |
| `MinTopUp` | EPay 的最低充值值；TOKENS 显示模式下界面会进行对应换算 |
| `PayMethods` | 支付方式 JSON，可配置名称、图标、类型和方法名等信息 |

回调路径：

- 钱包充值通知：`<CallbackAddress>/api/user/epay/notify`
- 订阅支付通知：`<CallbackAddress>/api/subscription/epay/notify`
- 订阅支付返回：`<CallbackAddress>/api/subscription/epay/return`

EPay 钱包支付完成后的站内返回路径由系统使用 `/usage-logs`。EPay 是一种支付协议，不代表单一官方网站或唯一服务商，接入前应自行核实服务商身份、费率和安全性。

`PayMethods` 中的 `type` 具有分流作用：

- `stripe`：使用 Stripe 流程；
- `waffo_pancake`：使用 Waffo Pancake 流程；
- 其他值：作为 EPay 的支付类型发送给 EPay 服务。

### Stripe

Stripe 在已确认合规并配置以下三个值后可用：

- `StripeApiSecret`：API Secret，通常以 `sk_` 或 `rk_` 开头；
- `StripeWebhookSecret`：Webhook 签名密钥，通常以 `whsec_` 开头；
- `StripePriceId`：Stripe 后台创建的 Price ID。

Webhook 地址为：

```text
<ServerAddress>/api/stripe/webhook
```

在 Stripe 后台至少订阅以下事件：

- `checkout.session.completed`
- `checkout.session.expired`

| 设置项 | 说明 |
| --- | --- |
| `StripeUnitPrice` | 每购买 1 个系统 USD 余额对应的本地货币金额，默认 `8.0` |
| `StripeMinTopUp` | Stripe 最低充值值，默认 `1` |
| `StripePromotionCodesEnabled` | 是否允许用户在 Stripe Checkout 输入优惠码 |

后端会使用 Webhook Secret 验证回调签名。单次 Stripe 充值请求的金额上限为 `10000`（按页面金额单位逻辑）；如果用户提交的成功或取消返回地址不属于可信域名，后端也会拒绝该地址。

### Creem

Creem 充值在已确认合规，且 `CreemApiKey` 和非空 `CreemProducts` 已配置时可用。要实际接收并验证 Webhook，还必须配置 `CreemWebhookSecret`。

Webhook 地址为：

```text
<ServerAddress>/api/creem/webhook
```

`CreemTestMode` 用于切换 Creem 测试 API 与生产 API。产品配置是 JSON 数组，例如：

```json
[
  {
    "name": "Basic",
    "productId": "prod_xxx",
    "price": 10,
    "quota": 500000,
    "currency": "USD"
  }
]
```

产品 ID、价格、货币和发放 quota 必须与 Creem 后台产品及站内售卖方案一致。测试完成后切换生产模式时，应同步替换生产环境的 API Key、Webhook Secret 和产品 ID。

### Waffo

Waffo 需要先确认支付合规并开启 `WaffoEnabled`。随后根据 `WaffoSandbox` 选择的环境配置完整凭证：

| 环境 | 必需凭证 |
| --- | --- |
| 生产 | API Key、RSA Private Key、Waffo Public Key |
| 沙盒 | Sandbox API Key、Sandbox RSA Private Key、Sandbox Public Key |

其他主要设置：

| 设置项 | 说明 |
| --- | --- |
| `WaffoMerchantId` | 商户 ID |
| `WaffoCurrency` | 当前表单只读，默认 `USD` |
| `WaffoUnitPrice` | 每购买 1 个系统 USD 余额对应的网关货币金额 |
| `WaffoMinTopUp` | 最低充值值，前端要求至少为 `1` |
| `WaffoPayMethods` | 服务端允许的支付方式 JSON，客户端不能任意覆盖此列表 |
| `WaffoNotifyUrl` | 自定义通知地址；留空时使用默认 Webhook |
| `WaffoReturnUrl` | 自定义支付返回地址；留空时返回钱包页 |

默认地址：

- Webhook：`<ServerAddress>/api/waffo/webhook`
- 支付返回：`<ServerAddress>/wallet?show_history=true`

Waffo 回调通过 `X-SIGNATURE` 请求头验签。虽然配置中保留了货币字段，当前实现按 Waffo 接受 USD 的约束处理，设置其他显示货币前应先确认网关实际支持情况。

### Waffo Pancake

Waffo Pancake 没有单独的 Enabled 开关。确认支付合规，并配置以下三项后，钱包充值流程才会启用：

- `WaffoPancakeMerchantID`
- `WaffoPancakePrivateKey`
- `WaffoPancakeProductID`

测试和生产 Webhook 必须分别配置：

```text
<ServerAddress>/api/waffo-pancake/webhook/test
<ServerAddress>/api/waffo-pancake/webhook/prod
```

Pancake 事件携带的 mode 必须与 URL 中的 `test` 或 `prod` 一致，否则不会入账。Webhook 使用 `X-Waffo-Signature` 验签。

管理页支持以下工作流：

1. 输入 Merchant ID 和 API Private Key，验证凭证并拉取商店与产品目录。
2. 选择已有商店，或者创建 Store 与一次性 Product。
3. 绑定用于钱包充值的 Store 和 Product。
4. 保存绑定信息和 Return URL。

钱包充值只绑定一个一次性 Product，系统会在每次 checkout session 中覆盖本次价格，不需要为每个充值金额预建 SKU。订阅计划不使用这个钱包 Product；每个订阅计划有独立的 Pancake product，需要在订阅管理中单独配置或创建。

`WaffoPancakeReturnURL` 用于创建产品时设置 SuccessURL／支付返回信息。私钥输入留空会保留原值。

> **截图建议：** 支付合规状态与各网关折叠面板。分别截取测试环境配置、回调地址和启用状态，不要展示任何完整密钥、商户私钥或签名内容。

## 充值金额与优惠规则

### 快捷金额

`payment_setting.amount_options` 是钱包页面显示的快捷充值金额 JSON 数组，例如：

```json
[10, 50, 100, 200]
```

该列表只提供快捷选择，不会限制用户只能充值这些金额。最低金额仍由具体网关的 `MinTopUp` 或 `UnitPrice` 相关规则校验。

### 金额优惠乘数

`payment_setting.amount_discount` 是按用户原始充值金额匹配的 JSON 对象：

```json
{
  "100": 0.95,
  "200": 0.9
}
```

配置值是**乘数**，不是百分比：

- 小于 `1`：降低实付金额，例如 `0.95` 表示按原价的 95% 收取；
- 等于 `1`：不调整；
- 大于 `1`：提高实付金额；
- 非正值：运行时通常回退为 `1`。

规则按原始请求金额的整数值匹配。TOKENS 显示模式下，要特别核对用户输入的是显示的 Token 数还是换算后的金额。

网关最终金额通常还会综合以下因素：

```text
原始充值值 × 金额优惠乘数 × 用户分组充值倍率 × 网关单价
```

不同网关对金额、货币和产品的处理有所差异，以上公式用于理解组成项，最终应以网关结算页与站内订单记录的结果为准。

## 签到奖励

| 设置项 | 配置键 | 说明 |
| --- | --- | --- |
| 启用签到 | `checkin_setting.enabled` | 是否向用户开放每日签到，默认关闭 |
| 最小奖励 | `checkin_setting.min_quota` | 每日奖励的最小内部额度，默认 `1000` |
| 最大奖励 | `checkin_setting.max_quota` | 每日奖励的最大内部额度，默认 `10000` |

每个用户每天只能成功签到一次，数据库通过用户 ID 和签到日期的唯一约束避免并发重复领取。如果最大值大于最小值，系统会在闭区间 `[min, max]` 内随机发放；否则固定发放最小值。

签到奖励会直接增加用户普通 quota，并记录系统日志。如果全局开启了 Turnstile，用户签到接口也会经过 Turnstile 校验。

<Callout type="warn">
  最小值大于最大值时保存不会自动报错，实际会固定发放最小值。启用签到前请再次核对范围和格式化后的额度，避免奖励远高于预期。
</Callout>

## 保存后的验证清单

完成配置后，按以下顺序验证：

- [ ] 保存后刷新页面，确认普通字段没有因逐项提交失败而部分回退。
- [ ] 使用一个测试模型分别发起短请求和较长请求，核对预扣、实际扣费和退款记录。
- [ ] 检查普通模型、缓存、图片、音频和工具调用是否采用预期价格。
- [ ] 使用不同用户分组测试模型扣费与充值倍率。
- [ ] 检查钱包、日志、订阅页的货币符号和金额显示是否一致。
- [ ] 在网关沙盒或测试模式创建小额订单，核对创建、回调验签、入账和订单状态。
- [ ] 从公网验证每个已启用网关的 Webhook 地址可访问，并确认反向代理保留请求体和签名头。
- [ ] 测试邀请注册与邀请额度转移，确认奖励进入正确的余额类型。
- [ ] 启用签到后用测试用户签到两次，确认同一天只能领取一次且系统日志存在记录。

## 常见问题

### 修改显示货币后，用户余额会被重新计算吗？

不会。显示模式和汇率主要控制界面格式化，内部 quota 不会因为切换 USD、CNY、CUSTOM 或 TOKENS 而被批量重写。

### 为什么保存密钥后再次打开页面看不到原值？

系统不会回显完整敏感值。留空保存通常会保留已有密钥；需要轮换时填写新密钥。不要使用占位字符覆盖真实密钥。

### 为什么支付网关字段完整，用户仍然无法充值？

先检查是否已由 Root 通过后台会话确认支付合规声明，再逐项检查该网关的启用条件、`ServerAddress`、Webhook、测试／生产环境和签名密钥。不同网关不能共用同一套启用条件。

### 为什么实际模型费用与倍率值不一致？

倍率不是直接的美元单价。按次价格、动态表达式、补全和缓存倍率、媒体用量、工具调用价格、分组倍率都会改变结果。请结合请求用量和日志逐项排查。

### 配置了快捷充值金额后，用户为什么仍能输入其他金额？

`amount_options` 只控制快捷按钮，不是允许金额白名单。最低值和上限由具体网关及后端校验决定。

### 邀请人为什么没有立即看到普通余额增加？

邀请人的奖励先进入邀请额度 `aff_quota`。达到至少一个 `QuotaPerUnit` 且满足支付合规要求后，用户才能将其转入普通余额。

### 签到奖励为什么每天都是最小值？

当最大值不大于最小值时，系统固定发放最小值。请检查最小值和最大值是否填反，以及两者是否使用了预期的内部 quota 单位。
